# Локальные нагрузочные замеры — Dev Social Network

> **Происхождение данных.** Таблицы ниже переписаны из сохранённых таблиц и временных интервалов технического журнала проекта (октябрь 2026). Это **не** логи production и **не** новый независимый тест. Исходные файлы замеров, генератор нагрузки и скриншоты дашбордов пока не опубликованы в GitHub, поэтому результат пока нельзя полностью независимо воспроизвести.

## 1. Kafka: разгрузка очереди, consumer concurrency 1 vs 3

**Что измерялось:** время обработки **заранее накопленных сообщений** Kafka, не скорость входящего HTTP, не latency доставки писем и не максимальная непрерывная нагрузка. Реальный брокер Kafka, 3 партиции, Spring Kafka listener, реальные классы бизнес-обработки; получение автора и JavaMailSender заменены имитацией ожидания (5 и 40 мс). Запуск отдельной JVM без полного Spring Boot-контекста.

**Окружение:** Windows 11, Java 17.0.19, Core i5-9600KF, 6 логических процессоров, heap ≤ 512 MiB. Для каждого варианта — прогрев 120 событий, затем 3×1 200 измеренных; порядок 1→3→3→1→1→3. Сообщения равномерно распределены по 3 партициям, отдельные тестовые топики/groups. **7 200 событий без учёта прогрева**.

| Метрика | Concurrency=1 | Concurrency=3 |
| --- | ---: | ---: |
| Измерено событий | 3 600 | 3 600 |
| Throughput | **15,38 событий/с** | **46,93 событий/с** |
| Диапазон throughput по трём прогонам | 15,25–15,57 | 46,83–47,07 |
| Среднее время разгрузки 1 200 событий | 78,03 с | 25,57 с |
| Одновременно активных отправок — peak | 1 | 3 |
| Ошибки | 0 | 0 |
| Повторные обработки | 0 | 0 |
| Остаток после прогона | 0 | 0 |

Ускорение = **46,93 / 15,38 = 3,05×** (около +205% throughput). Результат **условен**: имитация блокирующего I/O позволяет перекрывать ожидания, ключи равномерно распределены по 3 партициям.

### Latency: отличать обработку одного события от ожидания в очереди

Процентили p95/p99 рассчитаны по сырым 3 600 измерениям каждого варианта (метод ближайшего ранга), **не** усреднением перцентилей прогонов.

| Метрика | Concurrency=1 | Concurrency=3 |
| --- | ---: | ---: |
| Обработка одного события — средняя | 62,12 мс | 61,22 мс |
| Обработка одного события — p95 | 67,69 мс | 66,39 мс |
| Обработка одного события — p99 | 71,63 мс | 71,66 мс |
| Имитация отправки — p95 | 53,35 мс | 51,34 мс |
| Имитация отправки — p99 | 55,45 мс | 54,64 мс |
| Завершение от начала разгрузки очереди — p95 | 74,30 с | 24,30 с |
| Завершение от начала разгрузки очереди — p99 | 77,36 с | 25,33 с |

**Интерпретация:** индивидуальная обработка занимает примерно те же ~61–62 мс, но время ожидания сообщения в очереди резко сокращается благодаря параллельной работе трёх consumer. Не следует утверждать, что latency **одной отправки** ускорилась в 3 раза.

Три записанных перекрывающихся временных интервала из одного прогона, отсчёт от запуска обработки очереди:

| 1000000 | 0 | Consumer 1 | 13,9595 | 61,4270 |

**Общее пересечение:** с 13,9744 до 61,4270 мс. Дополнительное подтверждение — Prometheus scrape (каждую 1 с) зафиксировал `notifications.email.peak=3`. Множественные имена потоков без временного пересечения не считались доказательством.

## 2. Redis Pub/Sub → локальная SMTP-заглушка: наблюдаемость и нагрузка

**Что измерялось:** обработка события по цепочке Publisher → Redis Pub/Sub → notification_service → Feign-заглушка → JavaMailSender → локальный SMTP-стаб. Никакого реального массового Gmail; создание постов через HTTP и PostgreSQL **не включены**.

Окружение: Linux / Docker, лимит Java-контейнера **2 vCPU и 1 GiB RAM**; заглушки и генератор нагрузки размещены в общей JVM с приложением. Прогрев 15 с, 4 уровня конкурентности × 3 замера по 20 с = **57 600 событий**.

| Конкурентность | Throughput, событий/с | Средняя latency, мс | p95, мс | p99, мс |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 20,6 | 48,5 | 53,1 | 55,8 |
| 8 | 165,6 | 48,2 | 54,3 | 58,0 |
| 16 | 344,4 | 46,3 | 61,9 | 94,6 |
| 32 | **427,1** | 73,7 | **171,8** | **201,2** |

С 16 до 32 concurrency: throughput вырос примерно на 24%, а p95 почти в 2,8 раза. **Приоритет зависит от SLA:** максимум событий/с и сбалансированная задержка — разные цели. Здесь c=16 обеспечивал лучшую компромиссную точку.

### Отказы и восстановление

- При добавлении **200 мс** искусственной задержки SMTP и c=16: **66,8 событий/с, p95=252,9 мс**.
- **20** смоделированных SMTP-ошибок → **20** ошибочных записей в метриках, без ложного увеличения success.
- После восстановления SMTP-стаба **100 новых** событий успешно обработались. Ранее отклонённые события **не** повторяются автоматически.
- Отдельный тестовый Prometheus (scrape 2 с) выполнил **134/134** успешных сбора, максимальный scrape duration **61,6 мс**.
- Диагностический Windows-прогон с 32 `BindException` / TIME_WAIT **не входит** в успешные Linux-метрики.

Конфигурация: [Actuator/Micrometer](https://github.com/VladHvedchenya/notification_service/blob/dev/src/main/resources/application.yaml), [Micrometer instrumenting](https://github.com/VladHvedchenya/notification_service/blob/dev/src/main/java/faang/school/notificationservice/metrics/EmailNotificationMetrics.java), [Prometheus](https://github.com/VladHvedchenya/infra/blob/master/monitoring/prometheus/prometheus.yml), [Grafana dashboard](https://github.com/VladHvedchenya/infra/blob/master/monitoring/grafana/dashboards/notification-service.json).

## Ограничения выводов

1. Ни один из двух тестов **не** измеряет HTTP RPS всего приложения.
2. SMTP и `user_service` имитируются, для Kafka стенда значимы моделируемые задержки; результаты **не подтверждают** performance Gmail.
3. Kafka-тест — **drain заранее созданного backlog**, не непрерывный steady-state при фиксированной входной скорости.
4. `p95` и `p99` определяют границу распределения, а не среднее; нужно указывать, **какая именно задержка** измерялась.
5. В Kafka `post.created` публикуется после успешного PostgreSQL commit, но без атомарной пары DB+Kafka. `exactly-once`, идемпотентный email, retry/DLQ и failover Kafka кластера **не доказаны**.
6. Текущие таблицы — перенесённые агрегаты из журнала; для полного независимого аудита ещё нужны сырой CSV, сценарий генератора, лог параметров стенда и настоящие скриншоты Grafana.
